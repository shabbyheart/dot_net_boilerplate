# ADR-0030: File storage

- Status: Accepted
- Date: 2026-10-20

## Context

Most products built on this boilerplate need users to upload and download files (attachments, documents, images).
Nothing stores binary content today, and the 1 MB request limit (ADR-0024) rules out uploads of useful size. File
content must stay tenant-isolated like every other tenant data (ADR-0010), and the storage backend differs by
deployment (a disk or volume locally, an object store in the cloud).

## Alternatives considered

- **Where content lives:** in PostgreSQL (`bytea`: transactional, but bloats the database, backups and memory), or
  **behind a storage port**, with metadata in PostgreSQL and content in a backend chosen by Infrastructure.
- **Backends now:** a cloud SDK (S3, Azure Blob) from the start (a vendor package and decision before anyone needs
  it), or **a local-disk implementation only**, with cloud backends added later as second implementations of the port.
- **Storage keys:** derived from the user's file name or a tenant path (path traversal risk, renames), or **the file's
  id**, generated by the application. Tenant isolation comes from the metadata row, which is tenant-owned.
- **Deleting content:** in the request after the commit (lost on a crash), inside the transaction (a remote call
  while it is open, ADR-0011), or **through the outbox** (ADR-0019): idempotent and retried after the commit.
- **Upload size:** raise the global body limit, or **raise it only for the upload endpoint**, to the configured
  maximum file size.
- **Trusting the content type:** detect it from the content (magic numbers, a library), or **accept only an
  allowlist of declared types and always serve downloads as attachments with `nosniff`**, so browsers never render
  them in the API's origin.

## Decision

**Model and port**

- `StoredFile` (tenant-owned, auditable) holds the file name, content type and length. Its storage key is its id
  (32 hex digits); no user input reaches a storage path.
- `IFileStorage` (Application) writes, opens and deletes content by key. Infrastructure provides `LocalDiskFileStorage`
  under `Storage:Local:RootPath`. It resolves every key inside the root, writes to a temporary file and renames it,
  and treats deleting a missing file as success.
- Without `Storage:Local:RootPath` the API starts, and uploading or downloading answers 409, as invitations do
  without their accept page (ADR-0027).

**Endpoints** (`/api/v1/files`; permissions `files.read`, `files.manage`)

- `POST` (multipart, field `file`): validates the name, the declared content type against
  `Storage:AllowedContentTypes` and the length against `Storage:MaxFileSize` (default 10 MB, at most 100 MB), then
  writes the content and saves the metadata. If saving fails, the content is deleted again. Only this endpoint
  accepts bodies up to the maximum file size plus multipart overhead; every other endpoint keeps the 1 MB limit.
- `GET` (paged, newest first), `GET {id}`: metadata.
- `GET {id}/content`: the content as an attachment (`Content-Disposition: attachment`), with the stored content type
  and `X-Content-Type-Options: nosniff` (ADR-0024).
- `DELETE {id}`: deletes the metadata and enqueues `files.delete-content` in the same transaction; its handler
  deletes the content after the commit.
- File names are reduced to their last path segment, stripped of control characters and limited to 255 characters.
- File changes are not recorded in the audit log: files are ordinary tenant data, like projects (ADR-0028).

## Consequences

- Features can attach files without a vendor dependency; a cloud backend is one new class and an ADR for its package.
- Content and metadata are not in one transaction. A crash between writing content and saving metadata, or a failed
  cleanup, leaves unreferenced content on disk; nothing removes it automatically yet. A deleted file's content stays
  until the outbox message is delivered.
- Local disk storage is only correct on a single instance or with a volume shared by all instances. Deployments with
  several instances need a shared volume or an object-store implementation.
- The declared content type is trusted within the allowlist. A file can claim to be a PNG and contain anything; it is
  only ever served as an attachment that browsers do not sniff. Virus scanning is not included.
- There are no quotas per tenant; storage use is bounded only by the file size limit and rate limiting.
- Readiness does not check the storage backend.
